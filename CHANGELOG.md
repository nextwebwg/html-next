# Changelog

## expressmark 0.0.1

- Establish the independently versioned Expressive Markdown package with ESM/types, installed-consumer verification, and a protected release workflow. This is a name reservation with no public API; parsing and writing are not implemented.

## 1.0.0-alpha.59

### Added

- Live, compiled native and Vue components accept `<state from>` for an editable value initialized from the first available input. Early accepted edits win, record/list seeds are copied, refreshes preserve drafts, and rendered-form adoption retains initialization ownership. React and Svelte state initialization is still in progress.
- `@nextwebwg/html-next/bindings` supplies selected-input data drivers over the renderer's typed input SDK. `BindingScope` owns reads, cancellation, refresh, subscriptions and scheduling without another accepted-value store. `bindModule` adapts static providers or a passive per-instance `create()` to named browser `connect`, with separate preparation for application hosts. Read snapshots match source, selected input and adopted input revision; handled failures transfer without an automatic duplicate request. See [the driver API](packages/html-next/docs/binding-drivers.md).
- Binding selectors read declared state, computed values and context aliases through their existing state namespace. The input SDK exposes read-only declaration values and availability alongside writable props, and status-only computed changes notify dependent providers in live, native, React, Vue and Svelte output. Behavior-only binding modules work without a props boundary, keeping passive factory state across reconnects.
- Live, compiled native, React, Vue and Svelte output renders asynchronous typed props and computed values with `$await`/`$error`/`$else`, including named status and error aliases. Computed values and conditional parent bindings follow the prerequisites each evaluation reads. Fixtures override sources, defaults stay available, and refreshes preserve success DOM. Data drivers can import the renderer-neutral SDK from `@nextwebwg/html-next/inputs`.
- Component definitions accept `module="./behavior.js"` and a named `connect(host, { signal })` export. The live loader, native output, React, Vue, Svelte, package assembly, Vite integration and HTMLKit resolve the module and run its browser activation on each connection, preserving instance state. Deactivation cancels its signal and releases cleanup, including late async cleanup and connection-owned subscriptions. Server rendering leaves browser behavior unloaded. Generated host declarations include `Connect`; existing `controller` callbacks retain their once-per-instance behavior, and declaring both forms is an error.

### Fixed

- Preserve selected prop coercion from an invocation's HTML bootstrap while carrying typed input availability, keep `default()` fallbacks available, and retain accepted React computed values after invalid expression results.

### Breaking

- `nullable` is no longer a declaration attribute, on a `<prop>`, a `<state>` or a nested field. A declared value keeps its type, as a reflected attribute such as `tabIndex` does ([Types](https://nextwebwg.org/declarative-components/types#null-and-missing-values)): a prop with a `default`, or a state with a `value`, always reads as its type, and null clears it back to that default or value; a prop or state with neither reads null until it is given one. A declaration with `nullable` is `HC013`, which says to remove it (the live parser warns and reads the declaration without it). To migrate, delete `nullable`; for a field written `required nullable`, delete both, since a missing field reads null.

### Added

- `host.reset(name)` returns one state to its declared `value`, a fresh copy of an object or list, or to null without one; `host.reset()` resets every state in one batch. A name that is not a declared `<state>`, such as a computed, context or prop, throws a `TypeError`. It notifies as any write does, only when the value changes. Typed hosts type `reset` with the component's state names. The live runtime, compiled Vanilla output and converted Vue, React and Svelte components have it.

### Changed

- A null or undefined prop clears it to its `default`, or to null without one, whether it comes from a bound expression, a framework prop or `componentRegistry.update`; it is no longer an explicit input. Vue, React and Svelte passed a null prop through even when it had a default.
- A null or undefined write to a state, from a controller, `<set>` or `bind:`, reverts a state with a `value` to that value, and a field below a state to its value in the state's declared `value`, or to null where that has none; a state without a `value` stores null. A null write is never wrong-typed, so it never warns `HR007`; a closed Looma Disclosure with no `headingLevel` no longer warns. A present value of the wrong type still warns.
- A bound control that the user empties reverts its state to its declared `value` without that value being written back into the control: the field stays empty while the state reads its value, until the state takes another value from elsewhere. The live runtime, compiled Vanilla output and converted Vue, React and Svelte components behave the same.
- Typed hosts: a state's setter takes `T | null | undefined`; a state with a `value` reads `T`, and one without reads `T | null` (it was `T | undefined`). A React state without a `value` starts as null, as in the other targets. An optional object field that is null reads as missing and is typed `T | null`.
- Generated Vanilla modules carry their states' declared values, and the direct js-framework-benchmark entry grows by 158 B gzip.

A browser test runs the live runtime, compiled Vanilla output and converted Vue, React and Svelte components through a null prop returning to its default, null and undefined writes to states with and without a `value` at the root and below, a `<set>` of null, `host.reset` with and without a name and with a name it refuses, an emptied number input bound to a state with `value="0"` that stays empty while the state reads 0 and shows a later write, and a wrong-typed write that still warns once.

### Fixed

- A bound slot prop is checked in full against its declared type, as an [accepted value](https://nextwebwg.org/declarative-components/javascript#accepted-values-and-prop-inputs) is, in the live runtime, compiled output, Vue, React and Svelte. An object type is closed unless it is `open` ([Types](https://nextwebwg.org/declarative-components/types)), so a row with an undeclared field, a missing `required` field or a field of the wrong type is rejected. The live runtime and compiled output checked only the top-level kind, and took such rows. A rejected value warns `HR007` once per component, slot and prop: ``Slot `row` prop `row` does not satisfy its declared type `object({ id: string, label: string })`.`` The consumer's template then reads the prop as absent. Before this fix, the live runtime and compiled output failed with `HB001` when the first value was rejected. The live runtime, compiled output and Svelte also kept the last accepted value, where Vue and React already read it as absent. A bound value that reads nothing and fails its type is an `HT008` error when the definition is read. The warnings are the same in development and production builds. A test renders an extra field, a missing field, a wrong field type and a row that stops conforming in all five targets, in Chromium, Firefox and WebKit, with development and production bundles. A parser test covers the `HT008` error.

## 1.0.0-alpha.58

- Expressive Markdown tooling has moved to the independent [`nextwebwg/expressmark`](https://github.com/nextwebwg/expressmark) repository and is no longer part of this workspace.

### Added

- `HY007` warns about a component style rule whose subject is a nested component's root, which the rule never matches because a component styles its own root: `x-item:state(on) { … }`, `.row x-item`, `:slotted(x-item)`, or a component's own tag in its styles. The warning suggests conditioning one of the component's own elements on the nested one, as in `x-item:state(on) + label`, or setting a custom property the nested component reads; for its own tag, `:host`. `check`, the Vite plugin and the converter report it with the graph's other warnings, and the live runtime logs it once when it compiles the styles. Rules whose selectors hold `&` are left out, since their subject depends on the parent rule.
- Component styles condition their own markup on another component's state with `:state()`, as the [Style Scoping](https://nextwebwg.org/declarative-components/styling#state) chapter defines: `x-toggle:state(on) + label`, `.row:has(x-item:state(selected))` and `:slotted(li:has(x-item:state(selected)))` style the component's own elements while the nested or projected component's state holds. `:state(name of x-tag)` names the component; without `of`, the test matches any component in the graph that declares the state. Each root carries the states other components' styles test on it in `data-<tag>-state`, so a component with no styles of its own still writes them. The live runtime resolves these tests against the definitions it registers, and a stylesheet registered later makes existing roots start writing the state it tests. The build, the Vite plugin, `assembleComponentPackage` and the converter resolve them against the linked graph; `generateComponent` takes it as `definitions`, and `generateVueComponent`, `generateReactComponent` and `generateSvelteConversion` as `componentGraph`. Server rendering's `styleOwnership` includes these names, so hydrated roots keep writing them. A state no component in the graph declares, or an `of` tag outside it, is `HY001`; such a test without a graph is `HY006`. Tests cover the compilers, the live runtime with a later stylesheet and with server rendering, generated output from every target, and converted React and Vue graphs against the live runtime in a browser.
- `componentRegistry`, one registry of components for each document, modeled on `customElements`. `define(carrier)` registers the definition a `<template component>` carries and lowers that tag's invocations already in the document; `get(tag)` returns the registered definition, `{ tag }`; `whenDefined(tag)` resolves with it once the tag is registered; `upgrade(root)` lowers the registered invocations inside `root` synchronously; `create(tag, { props, content })` returns a new instance's native root, not yet connected, with each content node in the slot its `slot` attribute names; and `update(element, props)` sets an instance's props, rendered in its next flush, with `undefined` returning a prop to its default. Inserting a created root connects it, and its controller runs, as for any instance. The members never read `this`, so `const { create, update, whenDefined } = componentRegistry` works. `define` throws a `TypeError` for anything but a `<template component>`, a `SyntaxError` naming the first diagnostic's code for an invalid definition, and a `NotSupportedError` for a registered custom element's tag or a second definition of a tag (`HR001`); `whenDefined` rejects with a `SyntaxError` for a name that is not a valid custom element name; `create` throws a `NotSupportedError` for a registered custom element's tag, a `NotFoundError` for an unregistered tag and a `TypeError` for an undeclared prop; `update` throws a `TypeError` for an element that is not a component instance's root or an undeclared prop. `@nextwebwg/html-next`, `/runtime`, `/live`, `/browser` and `/generated-runtime` export it, with the `ComponentRegistry` class and the `ComponentInit` type; importing it reads no document, so server code imports it safely.
- Every HTML Next bundle on a page shares the document's registry. The live runtime registers each definition it discovers, loads or is given, so `create` works with no bundler; a compiled Vanilla DOM module defines its component when it is evaluated; and code creates and updates any registered component, whichever bundle defined it. `define` reads a carrier with the live runtime's parser, and throws a `NotSupportedError` on a page without one.
- A generated Vanilla declaration adds its tag to the global `ComponentTagMap`, as `HTMLElementTagNameMap` does for `createElement`, so `componentRegistry.create("x-button", …)` types its props and its root as `XButtonElement`.
- `packages/html-next/docs/component-registry.md` is a support note that says, for the live runtime, compiled Vanilla output and the Vue, React and Svelte targets, which `componentRegistry` behaviors each supports, each linked to its section of the proposal, along with the `sideEffects` rule that decides whether a bundle keeps a compiled module's registration.
- Tests cover each `componentRegistry` algorithm and error in the live runtime and compiled output in jsdom, an import of the package with no document, and, in Chromium, Firefox and WebKit, the live delivery and a compiled module as separate bundles each creating and updating the other's components, with the created root's controller running when it is inserted.
- A slot declares the props it gives its consumer's template, as a component declares its props ([Declaring a slot's props](https://nextwebwg.org/declarative-components/components#slot-props)): a `<slot name="summary">` in `<defs>` holds `<prop>` elements with the component `<prop>` vocabulary, `name`, `type`, `values`, `default`, `required` and a description, and renders nothing; without `name` it declares the default slot. An outlet gives each prop as a static attribute, converted by its declared type as an invocation's attribute is (`count="3"` with `type="number"` gives `3`), or bound with `from:`, whose value is given only while it conforms to the declared type, in the live runtime, compiled output, Vue, React and Svelte. Declared defaults fill the props an outlet leaves out. `definition.contract.slots` lists each declared slot's props, and the generated docs list them under the slot. Types follow: Vue's `defineSlots`, React's slot render-prop parameter, Svelte's snippet parameter and a Vanilla `<Name>Slots` interface type each prop, and a consumer's `<template slot>` reads `$label` and `$count` with their declared types. A test gives a template static, bound and default props in the live runtime, compiled output, Vue, React and Svelte, in Chromium, Firefox and WebKit; parser tests check each diagnostic, and installed Vue and Svelte consumers are type-checked against the declared props.
- `assembleComponentPackage` takes `hostTypes: true` and writes each controller's typed host, `<tag>.host.d.ts`, beside the component source that declares it, as the build and convert paths do, so a package typechecks its controllers in its own build. A test assembles a package with and without it.

### Breaking

- An outlet that gives props needs its slot's declaration: a prop the slot does not declare, props on a slot with no declaration, the same prop given both as an attribute and with `from:`, a missing `required` prop, and a static value its declared type does not take are each an `HT008` error that names the outlet, and an undeclared prop's error names the `<slot>` and `<prop>` declaration to add. A plain attribute on an outlet is a static prop, where it was an `HT008` "unsupported attribute" error. To migrate, declare each scoped slot's props in `<defs>`, such as `<slot name="row"><prop name="item" type="object({ id: string, name: string })" required>The row.</prop></slot>`; `type="unknown"` takes any value.

- A slot's name is a literal identifier, written on both sides ([Slots](https://nextwebwg.org/declarative-components/components#slots)). `<slot from:name="…">` is an `HT008` error that says to use one named scoped slot passing the item as a prop, such as `<slot name="option" from:item="$row">`; the live runtime, compiled output and the Vue, React and Svelte targets no longer render computed slot names. An outlet's `name` and a component child's `slot` attribute are spelled as an expression name, letters, digits and `_` without `-`, and a child's `slot` cannot be bound with `from:slot`; each is an `HT008` error, which suggests the camel-case spelling, such as `labelAction` for `label-action`. `slot=""` still assigns the default slot, and `slot` on an element that is not a component's child keeps its native meaning.

To migrate, give each slot an identifier name, `labelAction` for `label-action`, in its outlet and in every consumer, and replace a slot whose name is computed per item with one declared scoped slot that passes the item: `<slot from:name="concat('option-', $row.id)">` becomes `<slot name="option" from:item="$row">` with `<slot name="option"><prop name="item" type="…" required>…</prop></slot>` in `<defs>`, and a consumer's per-item elements become one `<template slot="option">` that reads `$item`.

## 1.0.0-alpha.57

### Added

- HTMLKit form actions. A server-rendered page's loader file exports `actions`, functions by name that answer a `<form method="post">` to the page: `default`, or the one a `?/name` in the form's `action` or a button's `formaction` names. An action receives the page loader's context, request, cookies and response included, and runs before every loader. Returning nothing answers 303 to the page's URL without the action's name (POST/redirect/GET); returning an object renders the page with it as props over the page loader's, such as `{ errors, values }`, with the status the action sets on `response.status`, such as 422; `redirect()` and `notFound()` work as in a loader. A page without `actions` answers a POST with 405 and an unknown name with 404. A build that finds `actions` on a prerendered page fails, naming the page and its loader file, and development reports the same error when one is posted to. The `PageAction` type describes an action, and `ServerModule.actions` the export.
- A POST to a page from another site gets 403 before any action runs: `Sec-Fetch-Site` must be `same-origin` or `none`, or, from browsers that don't send it, `Origin`'s host must be the request's, as Go's `CrossOriginProtection` decides. A request with neither header, such as one from `curl`, goes through.
- Client navigation submits a page's `POST` forms in place. It sends the form as the browser would, from the `navigate` event's destination and `formData`, after constraint validation, with the form's encoding. A redirect's page renders from the same response and replaces the submission's history entry; a page the action renders shows at the action's URL; focus moves to the first `autofocus` field, else the start of the page, as after a page load. Without JavaScript or the Navigation API, and for a form inside `data-hk-reload`, the form submits as a document, with the same result. Tests submit in place and as a document in Chromium, Firefox and WebKit, under the site's generated Content Security Policy.
- While a page renders in place, `<html>` has `data-hk-navigating`, and a form submitting in place has `data-hk-submitting` and `aria-busy="true"`, so pages show a pending indicator with CSS. Each goes when the navigation ends, fails, or is replaced. Tests check the attributes during a link navigation and a submission in Chromium, Firefox and WebKit.
- The HTMLKit guide has a Forms page, and Moving between pages has a section on showing that a page is loading.
- Each component that declares a controller gets a typed host, `<tag>.host.d.ts`, beside its definition. It exports `Host`, typed from the component's `<defs>`, and `Controller`, the controller module's default export, so a TypeScript controller writes `import type { Host } from "./checkout-form.host.js"` and a JavaScript one `/** @type {import("./checkout-form.host.js").Controller} */`. `Host` types `props` by accepted value; `state` as writable state, readonly computed values and context values typed from their provider; `data` with each resource's `.value` from its `type`; `refs` by element type, as a list inside `$each` and possibly `undefined` inside `$if`; the declared `slots` and `scripts`; `request` and `hasResponder` by declared request, with each detail and answer type; `dispatch` by declared event and detail type; and `on` for the component's own events and requests, those of the components its template uses, `connect`, `disconnect` and DOM events. The declaration is self-contained, and uses the type mapping of the Vanilla declarations and the framework targets. The Vite plugin writes it when a build or dev server starts, for the native and framework targets; `html-next-sync` writes it for the native target too; `html-next build` and `html-next-convert` write it; `buildComponents` and `convertComponents` take `hostTypes: true`; and `writeHostDeclarations(graph)` and `generateHostTypes(definition)` are exported. Installed and imported components are left alone, and a file of that name HTML Next didn't write stops the run with an error. Tests compile typed TypeScript and JSDoc controllers against it, and check the errors for a misspelled state name, a wrong request detail, an undeclared script and a wrong dispatch detail. The runtime is unchanged.

### Fixed

- Live hydration adopts the server's nodes in a fragment `<template>`: the body of a `<template $if>` or `<template $with>`, a `<template $when>` or `<template $else>` arm of a `$match`, and a plain `<template>`, at any depth and in any parent, such as `<p>`, `<span>`, `<a>`, `<button>` and `<label>`. It built new elements in their place, so a reference taken before hydration was disconnected. A row of a `<template $each>` adopts its nodes the same way. Compiled hydration already adopted them. Tests hold node identity through server rendering and hydration, live and compiled, in Chromium, Firefox and WebKit.

## 1.0.0-alpha.56

### Added

- HTMLKit generates the site's Content Security Policy from what its components declare, and every page carries it: `script-src` with `'self'` for HTMLKit's modules, controllers and same-origin declared scripts, the origin of each declared script any page, layout, component, the not-found page or the error page names, and a `sha256` hash of each inline head script (a plugin's `headScript` and `app/head.js`), plus `object-src 'none'` and `base-uri 'none'`. One policy keeps client navigation in place, since a document keeps the policy it loaded with. Built pages carry it as a `<meta http-equiv="Content-Security-Policy">` before any script, without the `frame-ancestors`, `report-uri` and `sandbox` directives a meta ignores. `htmlkit start`, `application.fetch` and `htmlkit dev` also send it as the `Content-Security-Policy` header, with every directive; the build writes it into the server entry, version 2, for `htmlkit start`. `RenderedHead.csp` is the site's `RenderedPolicy`, with its `header`, its `meta` and `reportOnly`.
- The `csp` option adds sources to any directive in CSP's own grammar, such as `{ "script-src": ["https://cdn.example/"], "connect-src": ["https://api.example"] }`. They join the generated sources and never replace them; a directive whose generated source is `'none'` takes the added sources in its place. `reportOnly: true` sends `Content-Security-Policy-Report-Only` instead, and built pages then carry no meta, since a meta can't report only. `csp: false` turns the policy off. A directive name that isn't lowercase CSP, a source list that isn't a list, or a source with a space, semicolon or comma is an error. The `ContentSecurityPolicyOptions` and `RenderedPolicy` types describe them.
- `htmlkit dev` reports each violation in the terminal and the browser console, with the page, the blocked URL, the directive and the `csp` line that would allow it. Where the policy restricts `connect-src` or `default-src`, development adds `ws:` for Vite's HMR socket, and where it restricts `style-src`, `'unsafe-inline'` for the styles Vite injects for CSS a module imports.
- The document client navigation renders a payload in has no `<base>`, which `base-uri 'none'` forbids; the next page's module URLs resolve against its URL.
- A `pages` entry with `alias: true` serves a page folder at a further prefix, such as the current docs at both `/` and `/v/current/`. Its pages are served and navigable there, left out of `sitemap.xml`, and each has a `<link rel="canonical">` to the same page under the folder's own prefix, unless the page sets one; an `hk:alias` of such a page names the same URL. `ApplicationRoute.aliasOf` is that page's own pattern. ### Breaking

- HTMLKit pages and layouts declare their head content as HTML Next head declarations in `<defs>`: `<title>`, `<meta>`, `<link>`, JSON-LD and declared scripts, bound to the component's props, state and data. HTMLKit's settings, `hk:layout`, `hk:label`, `hk:order`, `hk:navigation`, `hk:render` and `hk:alias`, are `<meta>` entries there too, and HTMLKit leaves them out of the head; `hk:page` stays at the top of the file. `renderComponents` renders the head with the page, so a title, a canonical link and each meta name or property come from the deepest component that declares them, a page's over its layout's, and any component on the page may declare head content. A component reached by a bare specifier, such as `@acme/ui/card.html` or `@/components/card.html`, is an imported component, whose page-wide head entries are left out with `HL011`. Server-rendered and prerendered pages, the not-found page and the error page carry the reconciled head with `data-component-head` on each managed element and a `<link rel="preload">` for each eager declared script, and hydration adopts it. Client navigation leaves the head declarations to HTML Next, which updates them once per page change, inside a view transition's update when there is one, and never runs a declared script twice; HTMLKit swaps only its stylesheets and an alias page's canonical link. Every document starts from `<meta charset="utf-8">` and a viewport meta, which a page's own viewport replaces.
- A `<title>`, `<meta>` or `<link>` placed directly in a `<template component>`, outside `<defs>`, is an `HS002` error in HTML Next and an HTMLKit error that names the component.
- A loader's `head` sets only `lang`; a `title` or `description` there is an error that names the loader. `RenderedHead` is `{ html, lang?, canonical?, scripts? }`, where `html` is the head's elements as HTML; its `title`, `description` and `elements`, and the `HeadElement` type, are removed. A page payload's `head` is `{ lang, canonical? }`.

To migrate a page or layout:

1. Move its `<title>`, `<meta>` and `<link>` elements, `hk:` settings included, into its `<defs>`. A component without `<defs>` gets one.
2. Write a bound title as text, `<title>{$title}</title>`; `$value` and other attributes are not head bindings. A `<meta>` binds `from:content` and a `<link>` `from:href`.
3. Replace a loader's `head: { title, description }` with props the component declares and binds, such as `props: { title }` and `<title>{$title}</title>`.
4. Replace a page's `<link rel="stylesheet">` with an `@import` in its `<style>`, such as `<style>@import "./page.css";</style>`.
5. A helper component that declared a title or description now sets it while it is on the page, as the deepest component; remove head content the page should own.
6. A page compiler (`pages.compile`) writes the page's head content and `hk:` settings into the component's `<defs>`.

### Changed

### Fixed

## 1.0.0-alpha.53

### Added

- Requests, as the [proposal's requests section](https://nextwebwg.org/declarative-components/javascript#requests) defines them: behavior a component asks its consumer for. A definition declares `<request name type returns>` in `<defs>`, with `<prop>` children for the detail and a `<returns type>` child for the answer in expanded form, and the contract lists it under `requests`. Its detail and answer may be `unknown` or `event` at the top level, an omitted `type` is `null` and an omitted `returns` is `unknown`. A controller asks with `host.request(name, detail, { signal, progress })`, which resolves to the answer, or `null` when nobody answers. `host.request` is present on the host of a component that declares at least one request, in the live runtime, compiled output and converted components alike, so calling it elsewhere is a `TypeError`. The detail is checked against `type` and the answer against `returns`; `null` always answers, and a mismatch or an undeclared name rejects with a `TypeError` and warns `HR007`. The request is a `RequestEvent` that bubbles from the component's root, and the nearest listener answers with `respondWith(value or promise)`, reports progress with `progress(loaded, total)`, and receives a `signal` that aborts with the asker's signal or when the asking component disconnects, which also drops a late answer. A request from inside a component whose controller has not yet run its synchronous body waits for it. An unanswered request is remembered; a page script announces a late responder with a bubbling `responder` event, or with `respond(target, name, fn)` exported from `@nextwebwg/html-next`, `/runtime` and `/browser`, and one document listener relays it, as a non-bubbling `responder` event, to each component inside the announcing element whose request went unanswered. A later `host.on(name, …)` relays the same way without an announcement, and `host.on("responder", …)` hears only that relay. The live runtime, compiled Vanilla output and converted Vue, React and Svelte components share these requests through the document, so any of them answers any other's. The build manifest lists a component with requests under the `request` capability, generated docs list its requests, and compiled `.d.ts` files type each one's event as `RequestEvent<Detail, Answer>`.
- Converted Vue, React and Svelte components accept a function prop for each request, named in camelCase (`mentionQuery`), with `(detail, { signal, progress })`, and its event form: Vue's `@mention-query`, React's `onMentionQuery` and Svelte's `onmention-query`. The host listens before the controller runs and reads the prop when a request arrives, so a new function answers the next request, and a prop or listener set later relays to the unanswered requests. The generated types give each prop the request's detail and answer types. A component that declares requests imports the generated `requests.ts`, and the request's checks use the props helper's typed-value check.
- The usage guide shows how a component asks its consumer: a mention lookup that aborts the query before it, an upload that reports progress, and late responders. A test holds the behavior in Chromium, Firefox and WebKit, in the browser runtime, compiled Vanilla output and converted Vue, React and Svelte components.

### Breaking

- HTMLKit metadata uses the `hk:` prefix: `hk:page`, `hk:layout`, `hk:label`, `hk:navigation`, and `hk:alias`. The old `htmlkit:` spelling is an error that names its replacement. Rendered layers have `hk-layer-N` ids, and the browser event is `hk:ready`.
- The navigation component is `<hk-nav>`, after the `<nav>` it renders, in `components/nav.html`. It and HTMLKit's other built-in components need no component link, and the `hk-` prefix is reserved for them.
- `@/` is the project root in component links, controllers, stylesheet imports, and loader imports. HTML Next's Node loader accepts an application `importMap`, as its browser loader does, and HTMLKit passes `@/` through it and to Vite.
- Ordering prefixes are a number and a dot, and always apply: `01.guide/02.install.html` routes to `/guide/install/` and orders navigation. The `routeOrdering` option is removed. A dash no longer marks an ordering prefix, so rename `01-guide` to `01.guide`; a name such as `2024-recap` keeps its URL.
- `$if`, `$with` and `$match` rebuild their content only when the decision changes, in the live runtime and compiled output alike. The decision is the `$if` result, the chosen `$match` arm, or the text of a dynamic slot name in the content. Any other change updates the content in place. Previously, any change to what the decision read rebuilt it. Under `<div $if="$count > 0"><input></div>`, changing `count` from 1 to 2 no longer replaces the `<input>`, so typed text, focus and selection survive. Nested components are no longer re-created. `$with` and `$match` aliases update in place. Compiled output also rebuilds a `$match` arm when a slot name inside it changes, as live does. React conversion keys nested `$match` arms, so switching between arms of the same shape renders the new arm afresh rather than reusing the old arm's elements.
- Attribute, class, style and text bindings, `$value` and `$html` write only a result that differs from what they last wrote, in the live runtime and compiled output alike. Previously the live runtime rewrote the same value whenever something the binding read changed, and compiled output did so for `$html` and for class toggles on an element that also binds `class`. An unchanged `$html` no longer replaces its content, so focus and selection inside it survive. Property bindings and bound control values still write each new result.
- A `<data>` read requests again only when one of its `from` parameters resolves to a different value. Previously any change to what a `from` parameter read restarted the request, even when the URL stayed the same. Reconnecting still requests.

### Added

- The optional `transitions` extension animates what `$if`, `$each`, and `$match` add, remove, and move. `$transition` takes a keyframes name (a built-in `fade`, `fly`, `scale`, or `blur`, or any `@keyframes`) with an optional duration, easing, and delay; leaving plays it in reverse. `$transition-name` gives an element an identity, so one element can morph into another. The Vite plugin builds it with `extensions: ["transitions"]`, and `html-next-check` with `--extension transitions`. Without the option the directives fail `HT024`; an unknown extension name fails `HN013`, and a malformed value `HT025`. The live runtime and Vue, React, and Svelte conversion warn and build without animation. Components that do not use the directives compile exactly as before; the shared support every compiled component bundles grows by 4 B gzip. See the new Transitions guide.
- Compiled components can hydrate server output. With `generateComponent(definition, { hydrate: true })`, a component's factory takes a server-rendered root as its third argument, `create<Name>(options, html, root)`, and binds that DOM in place instead of creating its own. Hydration restores the instance's props and state from `data-html-next-instance`, adopts conditions, list rows, slot ranges, fallbacks, scoped renderings and nested components where the server rendered them, and keeps control values, focus and selection edited before startup. Each root connects, and its controller runs, once the outermost hydration has finished, in document order. A block whose server markup does not match its template is created afresh in its place. Modules generated without the option are unchanged.
- The quick-start guide shows the Vue, React and Svelte component each adapter generates from its `counter.html`. `pnpm generate:quick-start` writes them, and `pnpm check:generated` fails when the guide shows output the converters no longer generate.

### Changed

- HTMLKit inlines an optional `app/head.js` as a classic script after each page's charset declaration and before its stylesheets, so it runs before first paint, for example to apply a saved color theme without a flash of the default one. Text that would end or nest the script (`<!--`, `<script`, `</script`) is rejected.
- HTMLKit applications serve pages through `application.fetch(request)`, which takes a native `Request` and returns a `Response` on Node, Deno 2.8+, and Bun. The development server uses it for every page, and CI runs it on Deno and Bun.
- The HTMLKit development server's component stylesheet links load again. Vite requests them with a `?direct` query that HTMLKit's virtual sources did not recognize, so they returned 404 and each dev page first painted without component CSS until its module injected the styles, fading any transitioned colors in.
- HTMLKit plugins add page formats. A plugin's `pages` compiler claims file extensions such as `.md` and turns each file into an HTML Next page resource; HTMLKit then routes, orders, watches, renders, and builds those pages like `.html` pages. While compiling, a page can resolve another page's URL with `page.href` and serve a referenced file with `page.asset`. A plugin's `config()` contributes options, including a layout whose loader is a module object and a `headScript` inlined before `app/head.js`.
- `pages` lists the page directories and the URL prefix each serves, defaulting to `app/pages` at `/`. One directory may serve several prefixes.
- Pages can set their navigation label (`hk:label`), stay out of navigation (`hk:navigation` with `content="hidden"`), and add alias routes (`hk:alias`). An alias never appears in navigation and marks its page's own entry current.
- HTMLKit's `css` option adds page-wide stylesheets to every page, such as `['@/styles/page.css']`, for rules like `html` and `body`. They load before the page is shown, in builds and in development.
- HTMLKit plugins compose with the site: page folders, stylesheets, and routes a plugin adds join the site's own instead of replacing them, and `app/pages` stays. A page folder can name its own `layout`, which its pages use unless they name one, so a plugin's layout no longer wraps the whole site. `optional: true` skips a folder that doesn't exist.
- HTMLKit has built-in `<hk-breadcrumbs>` and `<hk-pager>`, unstyled and accessible like `<hk-nav>` and needing no component link. Loaders get `breadcrumbs()`, the existing pages from the home page (or `from`) down to the current one, and `pager()`, the pages before and after it in navigation order.
- HTMLKit navigates between pages in place, as Nuxt does. After the first page hydrates, a link to another page under the base loads that page's browser module and its data payload, renders the page in the browser with the server's own steps, keeps every layout the two pages share with its DOM, state, and controller, and swaps the rest. A kept layout takes its loader's new props, so `<hk-nav>` marks the new page current. The title and head metadata follow the new page, and screen readers hear its title. It uses the Navigation API (Chrome 135, Firefox 147, Safari 26.2), so back and forward, scrolling, and focus behave as for document loads; older browsers and readers without JavaScript keep loading whole pages.
- Builds write each page's payload to `_htmlkit/pages/<route>/payload.json`, and `application.fetch` (so `htmlkit dev`) serves it from the same render: the head, and each layer's component, prop attributes, and loader state. Loader `data` stays private. A payload is about 0.5 KB gzip where the docs proof's HTML is 1.4 to 4.6 KB. A page whose payload is missing or fails, or that cannot render from it, loads from its static HTML, and one that cannot render in place at all (missing, failed, or redefining a component already on the page) loads as a document. `RenderedPage` gains `layers`, and the build manifest lists each page's shared `chunks`.
- The `prefetch` option chooses what links load before a click: `interaction` (the default) loads a page's payload and module when its link is hovered or focused for 80 ms or touched, and only shared chunks for links on screen; `visible` also loads payloads and modules for links on screen; `none` loads nothing. `data-hk-prefetch` on a link or an ancestor overrides it. Prefetching never runs a page's code. Other sites, other base paths, files, downloads, new tabs, modified clicks, same-page fragments, posted forms, and links inside `data-hk-reload` load normally. An author's `@view-transition { navigation: auto; }` animates client navigation too. The client and the runtime functions it uses add 4.4 KB gzip (10%) to the first page; `docs/client-navigation.md` records the design and measurements.
- HTML Next's `adoptRenderedProps(element, rendered)` applies the props a fresh server rendering recorded on a component root to a live instance a framework keeps, through the `updateComponentProps` channel, without resetting its state or DOM.
- HTML Next's `replaceProjectedNode(current, next)` replaces a node a live component projects into a slot, in the document and in the component's projection: the new node is marked for slotted styles, appears in `host.slots` and the rendered form, and is what the slot renders if it renders again. Replacing projected content with `replaceWith` left the component projecting the old node.
- HTMLKit names a page's shared-import stylesheet for its whole component graph. Pages under one layout shared a name, so a build linked every such page to the last page's styles, and development served whichever page rendered last.
- `buildApplication()`'s `browserInputs` lists only source files. It also listed HTMLKit's virtual component stylesheets, which a tool reading each input could not open.
- A parent that passes a child component the value it already has no longer re-runs the child's prop validity, or rewrites its `data-*` reflection, in the live runtime and compiled output alike. The `data-valid`, `data-invalid`, `data-user-invalid` and `aria-invalid` markers, and `data-*` prop reflections, are written only when they change. In the live runtime, a `$each` row keeps its `loop` record through list updates, and only the fields that change are written, so `$loop.index` readers no longer re-run when only the count changes.
- Vue, React and Svelte conversion follow the same rules for unchanged values. A `<data>` read requests again only when a `from` parameter changes; React previously also requested when only an `expr` parameter changed, and Vue and Svelte whenever a `from` parameter's inputs changed. In React, a computed value that recomputes to the same result no longer reruns the effects that read it. In Vue and Svelte, an effect that reads one prop no longer reruns when another prop changes. Writing a value read from `host.state` back to it is no change. Svelte attribute and style bindings write only a changed result.
- React conversion tracks what a controller reads from `host.state` path by path: `items.push(…)` or `items[1].name = …` no longer reruns an effect that read only `items[0].name`, while assigning a new list still does. A controller's `host.computed` notifies only when its value changes. Converted React inputs and textareas skip renders that change none of their props, so React no longer rewrites their `name`, `type` or default on every update, and bound controls take their authored defaults while mounting. In every converter, bound controls, select options and the `aria-invalid` mirror write their defaults only when they differ, and in Svelte a `NaN` that stays `NaN` counts as unchanged.
- A `<data>` read requests again when a whole list sent as a `from` parameter changes in place: after `tags.push("b")` or `tags[0] = "z"` under `<param name="tags" from:value="$filter.tags">`, in the live runtime and compiled output alike. Compiled output previously requested again only when a new list was assigned, and the live runtime tracked the list's items only as a side effect of building the request. A list passed whole to a child prop already followed its items in both.
- Compiled output no longer throws `TypeError` when a `$match` of two or more arms with no `$else` has chosen no arm and another value it does not read changes.
- A new guide page, Versions and stability, says that alpha releases follow the proposal's live draft and may break components, sets out what 1.0 will promise within a major version, and shows how a library declares the tools versions it supports (`peerDependencies` today; the planned `htmlNext.snapshot` and `htmlNext.extensions` fields) and how extensions will be enabled. The READMEs, the library publishing guide, and the release mechanics link to it.
- Converted Vue components read like hand-written Vue. The quick-start counter converts to `const count = ref(0)`, `count.value = 0`, a two-line checked `count.value + 1`, and `Count: {{ count }}`. Rendering and binding helpers (`nativeAttrs`, `checkHydratedRoot`, `acceptsWrite`, `isNumber`, `text`, `KeyedBoundary` and the rest) come from the shared `vue/host.ts` rather than being repeated in each component. A string, number, integer or boolean state with a conforming literal initial value is no longer checked on each read, since every write to it is checked in full; structured states keep their read checks, because a handler write checks only their own kind. Across the conformance corpus the generated Vue is 55 KB (previously 135 KB), and an application of all its components ships 16.8 KB gzip (previously 20.6 KB); a single small component bundled alone is about 100 bytes larger.
- Converted Vue components mark their style scope with classes rather than `data-component`: a styled component's root carries its tag as a class, the `@scope` root, and each component its template invokes carries its own tag, the scope's limit. A selector naming a component by tag selects that class. The proposal treats both as target styling markers.
- Converted Vue templates write text as authored, such as `Count: {{ count }}`, and follow Vue's whitespace handling: each authored run of ASCII whitespace renders as one space, and indentation at the start and end of an element's text goes, so `textContent` differs from the live runtime's where the source indents or repeats spaces. A space between an element and the text after it stays, and non-breaking spaces and `<pre>` and `<textarea>` text are kept exactly.
- Converted React components import their rendering and binding helpers (`text`, `RetainedValue`, `KeyedBoundary`, `cycleCheckedComputed`, `renderPlainSlot`, `warnUnless` and the rest) from a shared `react/render.tsx` instead of defining them in each component, where the expression helpers were re-created on every render. The output is formatted, and mixed template text is one template literal (``{`Count: ${text(count)}`}``), which renders as the single Text node the live runtime creates. As in converted Vue, each authored run of ASCII whitespace in template text renders as one space and indentation at the start and end of an element's text goes; non-breaking spaces and `<pre>` and `<textarea>` text are kept exactly. Across the conformance corpus the generated React is 43.8 KB gzip (previously 62.0 KB), and an application of all its components ships 21.4 KB gzip (previously 25.9 KB).
- Converted React components use the names their source declares. A `count` state is `const [count, setCount, getCount] = useLiveState(0)`, an `increment` handler is `function increment()`, and an element that only listens takes its ref from `useNativeEvents([...])`. A handler write is `const next = getCount() + 1` and one `acceptsWrite(...)` line, and a literal the state accepts is a plain `setCount(0)`. A root with nothing to attach takes `ref={rootRef}`, and state contexts render as React 19 `<Context value>` elements.
- Converted React and Svelte components skip the read check on a string, number, integer or boolean state with a conforming literal initial value, as Vue components and the compiled build do.
- Converted Svelte components read like hand-written Svelte. The quick-start counter converts to `let count = $state<number>(0)`, `count = 0`, a two-line checked `count + 1`, and `Count: {count}`, with `{#each rows as { item: n, index: i }}` loops and authored `$with` and `$match` aliases. Rendering and binding helpers (`rootAttributes`, `acceptsWrite`, `isNumber`, `text`, `retainedValue`, `writePath`, `setProperty` and the rest) come from a shared `svelte/render.svelte.ts` rather than being defined in each component, and the root's attributes, `data-component` token and `constructor`/`__proto__` attachment are one `{...rootAttrs()}` spread. Scripts are formatted; markup breaks lines inside tags, since Svelte renders whitespace between elements as a space. Text follows Svelte's whitespace handling, as in Vue; `<pre>`, `<textarea>` and `<option>` text is kept exactly. Across the conformance corpus the generated Svelte is 36.0 KB gzip (previously 61.9 KB), and an application of all its components ships 24.5 KB gzip (previously 31.9 KB); the counter bundled alone is 68 bytes larger.

## 1.0.0-alpha.29

### Added

- Svelte conversion for application and library output, including source-folder Vite imports, hydration, slots, and controller lifecycle behavior.
- Handler `$$event` references and the `event` payload type preserve native events, including when passed through another event's detail.
- `<dispatch target="ref">` sends native events to component-local refs. Collection refs receive one event per rendered element, with a shared payload evaluated once.

### Changed

- Controllers initialize once per component instance and use `host.on("connect", ...)` for setup and cleanup on each connection.
- Resource data lives under `host.data`; mutable and computed state live under `host.state`. Invalid and readonly writes warn and retain the accepted value.
- Prop styling uses `:host([prop])`; `:host-state()` selects mutable or computed state.
- Removed the unsupported `<method>` API and its generated element-method and checker bridges. Use reactive props and native events with controller listeners.

## 1.0.0-alpha.28
