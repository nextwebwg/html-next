# HTMLKit 1.0 definition
Created: 2026-10-14

HTMLKit 1.0 is an HTML-first application framework a Nuxt or Next.js developer can
adopt without missing the essentials. You write pages as HTML Next components in a
file tree. Data loads on the server. Pages render on the server or ahead of time
and become interactive through compiled components. Navigation between pages stays
in place. You deploy it as a static site or as a request server.

This plan defines the 1.0 feature set and the docs it needs. It also sets the
order of work: Looma's documentation site, the first real consumer (through
Markupress), decides what is built first, so the platform gets used while it grows.

## Authority and inputs

- **Owner direction (2026-10-14):**
  - align HTMLKit's MVP with Nuxt and Next;
  - put the essential, highest-value core features in 1.0;
  - prioritize what Looma's docs need first, so they apply pressure and validate
    the work.
- **References, verified 2026-10-14:**
  - Nuxt 4.6.1 and Next.js 16.4.1 (App Router);
  - the 34 features both treat as core, listed in "Reference audit" below.
- **Current state:** `origin/main` at 1.0.0-alpha.47 (`5866a81`), after compiled
  delivery and client navigation (#184, #201).
- **Consumer:** Looma's docs site (`threadlabs-studio/looma` `apps/docs`, Docusaurus
  3.9) moves to Markupress in staged builds served beside the current site. See
  [the Markupress 1.0 definition](https://github.com/threadlabs-studio/markupress/blob/main/docs/plans/2026-10-14-markupress-1.0-definition.md).

## What 1.0 means

A feature is in 1.0 when both reference frameworks treat it as core and a typical
content-plus-interactivity app needs it. It is out of 1.0 when it is advanced, or
when only one framework offers it. "Today" below describes `origin/main`.

### Routing

| # | Feature | Today | 1.0 |
|---|---|---|---|
| R1 | File routes from `app/pages`, `01.` ordering, page folders at prefixes | Present | Keep |
| R2 | Dynamic `[id]` with `entries()` for prerender | Present | Keep. Dynamic pages render on request without `entries()` (see D1). |
| R3 | Catch-all `[...slug]` and optional `[[...slug]]` | Missing | **In** |
| R4 | Route groups `(group)/` that order and label pages without adding a URL segment | Missing (throws) | **In**: Looma's sidebar categories need them |
| R5 | Nested layouts from the file tree (a folder's `layout.html` wraps its pages, and its parent's layout wraps that) | Partial (`routes` option only) | **In** |
| R6 | Layout per route (`hk:layout`, `layoutDefaults`) | Present | Keep |
| R7 | User-authored 404 page (`app/pages/404.html` through its layout), used by build, preview, dev and `fetch` | Partial (fixed text) | **In** |
| R8 | Error page (`app/error.html`) for loader and render failures, with a status | Missing | **In** |
| R9 | Redirects: a config table, plus `redirect(url, status)` from a loader | Partial (trailing slash only) | **In** |
| R10 | Middleware: `app/middleware.server.ts` runs before loaders and can redirect, rewrite, return a response, or set headers and cookies | Missing | **In** |
| R11 | Base path, and trailing-slash URLs | Present (trailing slash fixed) | Keep; document host behavior |
| R12 | Client navigation with prefetch, scroll restoration, view transitions and a live-region announcer | Present | Keep; add loading state (D6) |

### Data

| # | Feature | Today | 1.0 |
|---|---|---|---|
| D1 | `.server.ts` loaders for layouts and pages; result `props`, `state`, `data`, `head` | Present | Keep |
| D2 | Request-aware loaders: query, headers, cookies, status, `redirect()`, `notFound()` | Missing (`request` throws) | **In** |
| D3 | Server data forwarded to the page with no second fetch | Present (payload and adoption) | Keep |
| D4 | Server endpoints: `app/api/**/*.server.ts` exporting `GET`, `POST`, `PUT`, `PATCH`, `DELETE` and returning a `Response` | Missing | **In** |
| D5 | Form actions: a page's loader file exports `actions`. `<form method="post">` works without JS and enhances under client navigation, returning validation errors to the page. | Missing (405) | **In** |
| D6 | Pending UI during client navigation (a `hk:navigating` state and a CSS hook) | Missing | **In** |
| D7 | Client data: component `<data>` reads (HTML Next) plus `fetch` to endpoints, documented as the client-data story | Partial, undocumented | **In** (docs only) |
| D8 | Caching and revalidation: `Cache-Control` per route, and time-based revalidation of prerendered pages | Missing | Out: 1.1 (`Cache-Control` headers through middleware are in 1.0) |
| D9 | Streaming and suspense | Missing | Out |

## Out of 1.0

These ship after 1.0 or never, and the guide's limitations page lists them:
- ISR and revalidation;
- streaming;
- edge runtimes and host adapters;
- image and font pipelines;
- parallel and intercepting routes;
- i18n routing;
- component HMR;
- auto-imports;
- a module marketplace.

Each one is either advanced or offered by only one of Nuxt and Next.

## Acceptance examples

- **AE1 (R3, R4, R5).** `app/pages/docs/(guides)/01.intro.html` serves `/docs/intro/`
  under the `docs` and `(guides)` layouts, and navigation labels the group. A file
  at `app/pages/docs/[...path].html` matches `/docs/a/b/`.
- **AE2 (R7, R8).** A missing route renders `app/pages/404.html` with status 404 in
  dev, preview, the static build and `start`. A loader that throws renders
  `app/error.html` with status 500, and in dev it names the loader file and line.
- **AE3 (D2, R9, R10).** A loader reads `?page=2` and a cookie, and `redirect("/login")`
  answers 303. Middleware that rejects a path answers before any loader runs.
- **AE4 (D4).** `app/api/todos.server.ts` exporting `GET` and `POST` answers JSON
  under `start` and under the same request in dev.
- **AE5 (D5).** A `<form method="post">` on `/todos/` submits to its action with JS
  off, and under client navigation it updates the page in place without a full
  reload. Validation errors render beside the fields.
- **AE6 (X2, X3).** `htmlkit build && htmlkit start` serves server routes on request,
  prerendered routes from files, and assets with long cache lifetimes, with no Vite
  process running.
- **AE7 (S2, V8).** With `origin` set, `sitemap.xml` lists canonical routes only. A
  link to a missing page or `#anchor` fails the build, naming the source page.
- **AE8 (V1).** `npm create htmlkit@latest my-app && cd my-app && npm run dev` serves a
  page with a loader, an endpoint and a form, and `npm run build` succeeds.

## Order of work

Looma's staged migration (Markupress plan, stages 1–6) sets the order. Each step
ships independently.

1. **For Looma stage 1** (foundations, getting started, one component page):
   - R5 nested layouts from files;
   - R7 the themed 404;
   - V7 `buildEnd` and pre-build hooks, for `generate:api` and the preview runtime;
   - V9 the documented manifest;
   - docs corrections (below).
2. **For Looma stages 2–3** (component pages and the catalog): R4 route groups,
   S2 the sitemap, S3 `robots.txt`.
3. **For Looma stage 6** (parity gates): V8 the internal link and anchor check.
4. **Request-time core.** No Looma dependency, so it runs alongside the steps above,
   in this order:
   - X2 the production server and `start`;
   - D2 request-aware loaders, plus R8 errors and R9 redirects;
   - R10 middleware;
   - D4 endpoints;
   - D5 form actions, with D6 pending UI;
   - X3 per-route mode.
5. **DX:** V5 environment variables, V4 the error page, V3 CSS reload, V6 types,
   then V1 `create-htmlkit` and the starter. The starter goes last so it shows the
   finished 1.0 surface.
6. **Docs:** G1–G6 as the features land. The guide is publishable when G1 and G4
   are complete.

## Docs corrections before new pages

From the 2026-10-14 audit; these are small edits to land first.
- `routes.md`: the `/about` → `/about/` redirect happens in dev, preview and
  `fetch`; a static host decides for itself.
- `index.md`: `preview` takes its base from the build manifest and ignores
  `--base`. State the default port 3000, and that flags override config.
  `app/components/` is a convention, not a special folder.
- `routes.md`: head merging is by identity (same `name`/`property`, canonical, or
  alternate+hreflang). State the default title, `lang` and the allowed head tags.
- `loaders.md`: the context's `phase`, `breadcrumbs` and `pager`; what `entries()`
  requires; `.server.js` support.
- `navigation.md`: document each component's `label`.
- `versions.md`: HTMLKit does not yet pass `extensions`, so `transitions` is
  unavailable there. Remove the stale "needs compiled components first".
- `docs/client-navigation.md`: its measurements predate compiled delivery.
- README: move the maintainer material (proof apps, release setup) out of the user
  README.

## Owner decisions

1. **Request-time rendering is in 1.0** (X2, D2, D4, D5, R10). This follows the
   "essential core" direction and changes the README's "first production adapter
   generates static pages". Static delivery stays first in the order of work.
2. **Form actions** (D5) follow the Nuxt endpoint model, plus progressive
   enhancement under client navigation. Next.js-style server functions called
   from client code are out.
3. **Host adapters move to 1.1** (X5). 1.0 ships the Node server entry, static
   output and documented recipes.
